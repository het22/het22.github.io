# [추가] 1. 존재할 수 없는 상태는 애초에 만들 수 없도록 타입으로 제약을 준다

## 몇 번째 지적이었나

두 번째였다. 첫 번째는 넘어갔고, 두 번째에 같은 말을 다시 쓰고 있다는 걸 알아채고 문장으로 고정했다.

## 첫 번째: 주석으로 제한한 단계 타입

온보딩 가이드의 단계를 표현하는 타입이 있었다. 단계 종류는 다섯 가지였는데, 타입은 넓게 열려 있고 어떤 조합이 허용되는지는 주석에 적혀 있었다.

```ts
// highlight | link | windowOpen | ... 중 하나
export type Step = { type: string; ... }
```

주석은 컴파일러가 읽지 않는다. 주석이 허용하지 않는 조합도 타입은 통과시킨다.

```ts
export type Step = HighlightStep | LinkStep | WindowOpenStep | ...
```

이때는 "주석 대신 타입을 쓰자"는 한 줄 코멘트로 끝났다. 원칙이라고 생각하지 않았다.

## 두 번째: 기획서에 없는 간선

다단계 폼의 상태 머신이었다. 상태는 `step`과 `editStep` 두 필드로 표현됐고, 전이는 리듀서 액션으로 일어났다.

```ts
type State = { step: StepA | StepB | StepC; editStep?: EditX | EditY }
type Action = { type: 'GO'; to: State } | ...
```

문제가 두 층이었다.

- `{ step: 'C', editStep: 'X' }`처럼 기획서에 없는 조합이 타입상 표현 가능했다.
- `'GO'` 액션이 어떤 상태에서든 어느 상태로든 이동을 허용했다. 기획서의 전이도에는 간선이 일곱 개였는데, 코드의 전이도는 완전 그래프였다.

기획서의 전이도와 코드의 전이도를 같은 그래프로 놓고 비교하면 차이가 바로 보인다. 그 차이가 전부 "존재할 수 없는 상태"다.

```ts
type State =
    | { step: 'A' }
    | { step: 'B'; editStep: 'X' | 'Y' }
    | { step: 'C' }

type Action =
    | { type: 'NEXT' }
    | { type: 'EDIT'; editStep: 'X' | 'Y' }
    | { type: 'BACK' }
```

전이를 액션으로 열거하면 간선이 기획서와 같아진다.

## 왜 원칙으로 올렸나

두 사례의 공통점은 "제한이 타입 바깥에 있다"는 것이다. 첫 번째는 주석에, 두 번째는 기획서에 있었다. 타입 바깥의 제한은 코드를 쓰는 사람이 기억해야 하고, 기억은 리뷰에서만 검증된다. 같은 리뷰를 두 번 쓴 시점에, 이건 사람이 아니라 타입이 할 일이라고 판단했다.

## 참고하는 구현

react-query의 `UseQueryResult`가 이 원칙을 라이브러리 수준에서 실행한다. `status`를 판별자로 두어 `success`에서만 `data`가 확정된다. 다만 `const { isLoading, data } = useQuery()`로 구조분해하면 좁히기가 깨진다. 원칙을 지킨 타입도 소비처에서 뚫릴 수 있다.

## 적용하지 않는 경우

아직 없다. 타입으로 막았다가 기획 변경에 발목 잡힌 경험이 생기면 수정 글로 남긴다.

## 결과

(리뷰 반영 여부. 이후 기획 변경 시 타입 에러가 실제로 전이 누락을 잡아준 사례가 있으면 기록.)
